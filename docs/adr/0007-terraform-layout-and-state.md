# ADR 0007: Module + stamp + per-client config, state per client

- Status: Accepted
- Date: 2026-11-13

## Decision
```
terraform/
  modules/           small, single-purpose, versioned modules (no providers configured inside)
  stamps/client/     ONE root module = a complete isolated client environment
  platform/          root module for the shared AI Advisory platform subscription
  clients/<name>/    terraform.tfvars + backend.hcl + client.json (ring, environment)
```
- **New client = new folder** under `clients/`, ~30 lines of config. No copy-pasted Terraform.
- **One state file per client** (`<client>.tfstate`) in its own blob container (`tfstate-<client>`)
  in the platform subscription's state storage account: Entra ID auth only, shared keys off,
  versioning and soft delete on. State contains resource IDs and sometimes sensitive values, so it
  is isolated per client too: each client's deployment identity has a role assignment on its own
  container only. (Target state: private endpoint only, once self-hosted runners exist; see ADR 0003.)
- Modules are pinned by Git tag when they move to their own repo (`?ref=modules/key-vault/v1.2.0`).
  While the practice is small they live in this repo and the stamp references them by path.
- Provider versions pinned with `~>` in the stamp and locked via `.terraform.lock.hcl`.
- Naming follows the Cloud Adoption Framework abbreviations (`rg-`, `kv-`, `oai-`, `cae-`...)
  with `<client>-<env>-<region-short>`, generated by the `naming` module so it can't drift.

## Why not workspaces
Terraform CLI workspaces share one backend config and make it easy to apply to the wrong client.
Separate backend keys plus a per-client identity make the wrong-client mistake impossible rather
than unlikely.

## Why not one root module with `for_each` over clients
One plan touching every client means one bad change breaks everyone, one identity needs access to
every subscription, and state locking serializes all clients. Rejected.
